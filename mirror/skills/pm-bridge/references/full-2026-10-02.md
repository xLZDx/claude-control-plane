# PM Bridge

PM Bridge is a user-scope MCP server (`D:\Repo\pm-bridge`) available in every Claude
Code session on this machine, not just when the CWD is that repo. It exists to remove
manual copy-paste between Claude Code and a GPT/ChatGPT web session, and to give the
operator a "CEO management by exception" workflow across the D:\Repo child projects:
most decisions get made by Claude + GPT-PM without the operator, and only genuine
exceptions escalate to them.

## Tools

- `gpt_send(text, transport?, open_tab?, project?)` / `gpt_await_reply(transport?, timeout_s?, poll_ms?)`
  — send a message to GPT and get its reply. `transport` is `"clipboard"` (default,
  safe, needs one paste/copy from the operator) or `"playwright"` (opt-in, fully
  automated DOM control of chatgpt.com, real ToS/ban/fragility risk -- see
  `D:\Repo\pm-bridge\README.md` before defaulting to it for anything unattended).
- `gpt_ingest_reply(text)` — fallback: log a reply the operator pasted straight into
  the chat instead of via clipboard/DOM.
- `pm_bridge_session_start()` / `pm_bridge_session_end()` / `gpt_session_peek(project?)`
  — playwright transport only. Hold one browser session open across many send/read
  calls instead of open-close-per-call, for an async multi-conversation workflow (send
  to A, switch to B without waiting, check A later). No auto-timeout -- always call
  `pm_bridge_session_end` when the active block of work is done. See "Session mode"
  under the escalation ladder below.
- `pm_bridge_status(limit?)` — recent message history.
- `pm_log_decision({id, title, options?, recommendation?, reviewer_consensus?, verdict?, project?})`
  / `pm_decision_log(limit?)` — the cross-project decision log. Append-only: log a new
  record with the same `id` when a decision's status changes, never edit an old one.
- `pm_set_gate({project, gate_id, status, evidence?, notes?})` / `pm_gate_status({project})`
  — per-project gate tracking, independent of any single repo's own `core/DECISION_LOG.md`.
- `pm_delegation_matrix()` — read-only. **Check this before deciding whether something
  needs CEO escalation at all.** It is edited by the operator only; never write to
  `config/delegation_matrix.md` yourself, and never treat a GPT or Claude opinion as
  license to expand what's autonomous.

If these tools aren't available in the current session, the MCP server was registered
or updated after this session started -- tell the operator to restart Claude Code.

## Escalation ladder

For anything that isn't purely mechanical, reuse the **`agent-consensus`** skill's
round policy instead of inventing a new one -- classify risk (R0-R3), run an
independent round, reopen only contested BLOCKER/MAJOR findings, adjudicate. PM Bridge
adds two tiers on top of that ladder, only reached if the risk class and
`pm_delegation_matrix` say this is outside autonomous scope:

1. **GPT-PM adversarial round** — frame the proposed design/decision with your own
   reasoning, then send it via `gpt_send` with an explicit devil's-advocate instruction
   baked into the prompt (adapted from this environment's own `codex_review.py`):
   "Apply a devil's-advocate stance: actively look for reasons this proposal is wrong,
   incomplete, or will cause problems, rather than defaulting to agreement. If you
   genuinely can't find a real problem, say so plainly instead of manufacturing one."
   Read the reply via `gpt_await_reply` (or, during an active `pm_bridge_session_start`
   session, `gpt_session_peek` to check back on it non-blockingly while working on
   something else -- see "Session mode" below).
   - **Round policy -- NOT capped** (operator correction, 2026-08-22, `~/.claude/CLAUDE.md`
     §15): keep going until genuine, fact-grounded consensus, not a fixed number of
     rounds guessed in advance. Every round re-verifies against the CURRENT real state
     (local repo, VPS, git history, any other reachable primary source) -- never against
     a prior round's shorthand or residual memory of what an earlier round concluded.
     Surface a still-contested BLOCKER/MAJOR-equivalent objection to the operator only
     once disagreement is genuinely stable after real re-verification, not on a round
     counter.
   - Resolve to one of: ACCEPT (no real objection, or objection addressed and GPT-PM
     agrees) / MODIFY (you revised the proposal based on a real point) / an explicitly
     surfaced, fact-grounded disagreement that remains contested after real
     re-verification -- that disagreement moves to step 2.
   - Same discipline as the rest of this ladder: verify any factual claim GPT makes
     against the real repo/evidence before accepting it, every round. Not a panel seat,
     not blind agreement.
   - **Scope every review request as a full sweep, not a re-check of one finding**
     (operator instruction, reinforced live during Personal_Decision_Command_Center G3
     checkpoint 4 after a 7-round spiral where each round found one more defect in
     machinery the previous round's fix had just added -- see `~/.claude/CLAUDE.md` §17
     "one sweep, not one finding per round"). Every `review.js`/`gpt_send` scope note
     (inline or via `--scope-note-file`) must explicitly tell GPT-PM to search
     everywhere and always on its side: the whole gate's invariant, the whole
     mechanism, and every integration/code path touching it -- not just the diff's
     changed lines and not just the MAJOR/BLOCKER being remediated this round. State
     this from round 1, not only after a spiral is already visible.

   **Session mode** (`pm_bridge_session_start` / `pm_bridge_session_end` /
   `gpt_session_peek`, added 2026-08-22): for a multi-round or multi-project exchange,
   start a session once and hold the browser open across every `gpt_send`/
   `gpt_await_reply`/`gpt_send_and_await` call in that block of work instead of paying an
   open/close cycle per call -- lets you send into one project's conversation, switch to
   another without waiting, and check back later with `gpt_session_peek`. No
   auto-timeout: call `pm_bridge_session_end` yourself once the block of work concludes,
   or another process needing the same browser profile (e.g. `review.js` elsewhere) will
   queue and eventually time out. Reading a reply during or after a session (`gpt_await_reply`,
   `gpt_session_peek`) always returns whatever the last message currently is -- it does
   not block trying to prove the reply is new; fact-check the content instead of trusting
   freshness.
2. **CEO escalation** — only if you and GPT-PM still disagree on something in the
   `pm_delegation_matrix` "recommend, then escalate" tier, or GPT-PM itself is
   unavailable/unreachable for a decision that tier requires. Log it with
   `pm_log_decision` (verdict `"PENDING"`) and present it to the operator in the
   `DECISION D-<n>` format: recommendation, why, consensus so far, risks, and an
   explicit `APPROVE`/`REJECT` ask -- not an open-ended "what do you think?". When the
   operator answers, log a follow-up `pm_log_decision` record with the same `id` and
   the resulting verdict.

Most work never reaches step 1: if `pm_delegation_matrix` puts it in the autonomous
tier, decide it yourself and move on -- don't manufacture an escalation for routine
implementation, review, or gate calls.

## Reporting

Use this environment's mandatory **`html-report`** skill for the actual report
mechanics (RU+EN pair, copy button, provenance block). PM Bridge just defines which of
three report shapes to reach for, per the operator's original design:

- **Milestone report** — routine progress update for a project: gates completed since
  last report (pull from `pm_gate_status`), what shipped, quality signal, schedule/
  budget risk, and any CEO decisions pending. No action needed from the operator to
  read it.
- **Exception report** — one specific `DECISION D-<n>` that needs the operator's
  `APPROVE`/`REJECT`, per the escalation-ladder format above. Keep it to one decision;
  don't bundle unrelated exceptions into one report.
- **Portfolio report** — cross-project rollup when the operator wants the whole
  D:\Repo picture at once: one line per project (status, % autonomous, what's
  blocked), a short "CEO attention" list, nothing else. Pull project names/status from
  each project's own `pm_gate_status` and `pm_decision_log` filtered by `project`.

Routine one-paragraph "done" replies don't need any of this -- the html-report skill's
own mandatory-format rule already carves that out.
