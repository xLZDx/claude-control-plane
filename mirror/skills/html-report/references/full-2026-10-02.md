# HTML report — house format

Applies in **every** project, to every report with items to browse: review findings, audits,
status summaries. It does not apply to a routine one-paragraph "done" reply, which needs no report.

The three requirements below are operator instructions (2026-08-15, extended 2026-08-17). They are
not stylistic suggestions; a report missing any of them is not finished.

## 1. Two files, one link

Write **both**, always, with the same content and the same design:

| File | Language | Where it goes |
| --- | --- | --- |
| `reports/<NAME>.ru.html` | Russian | disk + git + published as an artifact + **linked in the reply** |
| `reports/<NAME>.html` | English | disk + git — the durable in-repo record |

Both files land in the current project's `reports/` directory (create it if absent; use the
session scratchpad only for a genuinely throwaway report) and **both get committed**.

**Show only the Russian one** (operator instruction, 2026-08-19). One report, one link: publish
the Russian file as an artifact and give that link plus its local path. Do not hand over an
English link as well — two links for one report is the noise the operator asked to remove. The
English file still gets written and committed, because the repo's own record stays English.

Per the global file-reference rule, the visible label of the local link is the full path.

Older reports in some projects use a `_ru.html` suffix. `report_conform.py` accepts both, but new
reports use `.ru.html`.

## 2. Copy-whole-page button

A button that puts the whole rendered report text on the clipboard. It uses
`navigator.clipboard.writeText` with a `document.execCommand('copy')` fallback — the artifact
iframe blocks the modern API in some hosts, so the fallback is a real path, not decoration. It
reports success and failure on the button itself, and its own label stays out of the copied text.

## 3. Provenance block under the header

Directly under the header: project name, absolute path of the project folder, git remote (plus
branch and short HEAD when the report is about a change).

**Do not hand-write either of these.** Run the injector — it is idempotent and derives the
provenance from git, so it cannot drift from reality the way retyped metadata does:

```bash
py -3 C:/Users/koros/.claude/tools/report_conform.py <repo>/reports/<NAME>.ru.html <repo>/reports/<NAME>.html
py -3 C:/Users/koros/.claude/tools/report_conform.py <repo>/reports --check   # verify, exit 1 if due
```

It inserts a single bar right after `</header>` holding the provenance list and the button, styled
through the page's own custom properties (`var(--surface, #fff)`), so it adopts whatever palette
the report already uses. Label language follows the filename; `--lang ru|en` forces it. Re-running
refreshes the block rather than stacking copies — that is also how you update provenance after a
commit.

If the tool reports `no-header`, the page has no `</header>` to anchor to: give the report a real
`<header>` element rather than pasting the block by hand.

## Rosetta-governed runs: planned / DoD / status, per item

Operator instruction, 2026-08-26: *"что было запланированно, какой дефинишен оф дан и сделано или
нет или частично с хвостами."*

When the report covers work that ran under a Rosetta plan, it must show, **for every planned item**:

| | |
| --- | --- |
| **Planned** | what the plan said, not a retelling of what happened |
| **Definition of Done** | the criterion GPT-PM set for that item -- not one written by the implementer |
| **Status** | done / not done / **partial** |
| **Tail** | for anything partial: exactly what remains, in a sentence someone else could pick up |

A report listing only finished work is a status *claim*, not a status report. Items that were
planned and then dropped stay in the table with their real status and the reason -- silence is how
descoping becomes invisible.

The plan itself is printed into the session as prose when it is opened and whenever it is revised
(never a JSON dump), and the decision log records the plan AND the outcome against it. See the
`rosetta` skill.

## Order of work

1. Load the `artifact-design` skill (the Artifact tool requires it) and write the content —
   Russian and English, same structure, with a real `<header>` and a `.wrap` container.
2. Run `report_conform.py` over both files.
3. Publish **the Russian file** with the Artifact tool. Same file path on redeploy keeps the URL;
   pass `url` to update an artifact from an earlier conversation.
4. Commit both files.
5. Hand it over **in the session**: the Russian artifact link, the Russian local path, and a short
   summary of the substance written directly in the reply. Never offer to open the file, never
   launch a browser, never raise a window — the operator reads it where they already are.
   No English link.
6. **Stop** — *unless PM mode is on.* A report is normally a handover point: wait for the operator
   instead of rolling into the next gate (operator instruction, 2026-08-19). **When PM Bridge
   orchestrator mode is ON, step 6 inverts: report, then continue** (operator instruction,
   2026-08-26 — see "PM mode" below). Nothing else in this list changes.

## This is enforced, not advisory

Four checks across two hooks make the format mechanical, so no session can quietly skip it:

- `~/.claude/hooks/report_gate.py` (PreToolUse) **denies `git commit`** once a repository has three
  commits after the last one touching `reports/`. A commit that carries `reports/` files always
  passes, so writing the report is the way through. Kill switch `CLAUDE_REPORT_GATE=off`.
- `~/.claude/hooks/report_due.py` (Stop) blocks the end of a turn on the same condition, once per
  HEAD. Kill switch `CLAUDE_REPORT_DUE_GATE=off`.
- The same Stop hook also checks the handover itself: if the reply names a local
  `reports/...ru.html` path with no `claude.ai/code/artifact/...` URL anywhere in the same message,
  it blocks — a local path alone is not a finished handover (operator instruction 2026-08-19, after
  a report was handed over twice with only the local path). Kill switch `CLAUDE_REPORT_LINK_GATE=off`.
- `report_gate.py` also **denies the next `git commit` or `git push`** if the session's own most
  recent complete handover (real path + artifact link, together) got no genuine operator reply
  since — a context-compaction boundary doesn't count. Step 6 above ("stop") was advisory until a
  Fitness_App session handed over a stop-the-line report, got no reply, and kept working: wrote a
  second report, committed, pushed. The operator only found out from a VS Code link-open popup, and
  asked why the session hadn't just stopped. See `_report_common.unanswered_handover` for exactly
  what counts as "answered." Kill switch `CLAUDE_REPORT_HANDOVER_GATE=off` (set by the operator in
  the environment before a session starts — a session cannot lift this on itself).

A fifth check runs the other way round: under PM mode, `report_due.py` blocks a stop **once** per
handed-over report to say "keep going" (see "PM mode" above). It has no kill switch of its own —
`/pm-bridge-mode off` is the switch — because a lever that silences a check which stops a session
should not also silence the one that keeps a session going.

All of them share their definition of unreported work with `~/.claude/hooks/_report_common.py`, and
all fail open on any internal error. If one fires, fix the actual gap — do not look for a way around it.

## PM mode — a report is a checkpoint, not a stopping point

**Whenever PM Bridge orchestrator mode is ON (`/pm-bridge-mode on`), step 6 above inverts: hand the
report over and keep going.** Turning that mode on already means a pre-authorized run is under way,
across projects — so a report inside it records progress, it does not ask permission to continue.

Operator instruction, 2026-08-26: *"надо убедиться что такое не будет повторяться ни на одном
проекте если включен пм режим, сессия может закончиться только тогда когда задача полностью
выполнена."*

What that means concretely, in every project:

- **Do not stop after a report.** Continue to the next gate in the same turn.
- **A session ends only when** the program is actually complete, **or** it is blocked on a decision
  that is the operator's alone under `~/.claude/CLAUDE.md` §4/§14 — irreversible operations,
  destructive deletion, force-push, secrets, production, real money, branch creation. Name that
  decision in one line when you stop for it.
- **Anything else that needs deciding goes to GPT-PM under §16**, not to the operator.
- The report FORMAT is untouched: both files, conformed, Russian published and linked. PM mode
  changes *when* you stop, never *what a report must contain*.

Why this exists: suspending the enforcement hooks was not enough, because the sessions that stopped
were **not being blocked** — they read step 6, correctly, and stopped on their own. One said so
verbatim when asked: *"Это не техническое ограничение, а сознательно встроенный чек-пойнт: скилл
html-report ... трактует связку «репорт + push» как обязательную точку хендовера."* The instruction
itself had to invert, so it now does, and `report_due.py` delivers that inversion as a one-time
nudge on the very turn a report is handed over (`_report_common.pm_mode_active`,
`report_due.pm_continue_reason`). The nudge fires once per report and never repeats, so it cannot
trap a session that genuinely must stop.

Detection is the orchestrator's own `state/orchestrator.json`, with liveness confirmed by probing
the port it advertises. A crashed orchestrator leaves that file behind, and a stale file must never
silently switch off a safety check — so anything uncertain reads as PM mode OFF. Turning it off is
`/pm-bridge-mode off`; there is no separate env switch, because the mode itself is the switch.

## Program mode — one report at the end of a long, pre-authorized run

"Write a report per closed gate" plus "stop after every report" adds up to "stop after every
sub-gate" — exactly wrong once the operator has already authorized a whole multi-gate program end
to end and does not want to be paged after each step (operator instruction, 2026-08-20).

If the operator's own message says the run should not stop after each sub-gate — e.g. "не
останавливаться после каждого сабгейта", "ОТЧЁТ: ТОЛЬКО В КОНЦЕ", "do not stop after each
sub-gate", "REPORT: ONLY AT THE END", "AUTONOMOUS PROGRAM AUTHORIZED" (see
`_report_common.PROGRAM_MODE_RE` for the exact patterns) — **program mode** is in effect for the
rest of that transcript:

- the unreported-work threshold check (both hooks) and the unanswered-handover check
  (`report_gate.py`) go quiet — sub-gates no longer need their own report or their own stop;
- write the ONE final report when the whole run actually finishes, following steps 1–6 above as
  normal, including the stop at the end;
- the artifact-link format check stays active regardless — program mode changes *when* a report is
  due, never what a report must contain once written;
- nothing else about the authorization contract changes: destructive ops, force-push, and every
  other safety protection are untouched. Program mode is not a second GO — it only tells this one
  skill's enforcement to stop nagging mid-program.

This is detected from a genuine operator message in the transcript, not an environment variable —
an env var has to be set before a session starts, which cannot cover "the operator says so
mid-run." A model cannot forge a `user`-typed transcript row, so this can't be self-authorized any
more than the existing "operator replied" unblock can. See `_report_common.program_mode_declared`.

## Verify before claiming done

```bash
py -3 C:/Users/koros/.claude/tools/report_conform.py <repo>/reports --check
```

Exit 0 with no `MISSING` lines means every report in the directory carries the mandated block. A
report that was never conformed is a defect regardless of how good its content is.
