# update-config

Global CLAUDE.md §21 ("Universal override: explicit, action-specific operator consent") draws one
hard line: chat consent overrides prose rules, but it cannot lift a mechanically enforced
`permissions.deny` entry in `settings.json`/`settings.local.json` -- only an actual edit to that
file does. §21 names this skill as the intended vehicle for that edit, specifically so the change
happens through a defined, logged procedure instead of an ad-hoc freehand edit. This skill is that
procedure. It does nothing else -- it is not a general settings/config manager.

**Read `C:\Users\koros\.claude\CLAUDE.md` §21 (search `## 21.`) before using this skill if you have
not already read it this session** -- this skill implements exactly its boundary, no more.

## When to use this

Only when, in the CURRENT conversation, the operator has already given explicit, action-specific
consent to change ONE (or a small, explicitly named set of) `permissions.deny` entries, for a
stated reason. This skill does not ask for that consent itself -- it exists because the consent
already happened; invoking it without that consent already on record in the transcript is a
misuse of the skill, not a shortcut around asking.

## What this skill will NOT do (refuse and explain instead)

- Touch anything in `settings.json` other than the `permissions.deny` array. No `allow` list
  changes, no hook registration changes, no other top-level key.
- Remove more than the specific entries the operator actually named. If the operator's request is
  broader than one file/pattern (e.g. "remove the .env deny rules" without saying which of `.env`,
  `.env.local`, `.env.production`, `.env.*.local`, or others), stop and ask exactly which entries,
  rather than guessing broadly. Conservative-by-default, always.
- Do a blanket "clear all deny rules" or "disable permissions" edit, ever, regardless of phrasing.
- Touch anything that is not a `permissions.deny` entry in the first place -- platform-level
  confirmations, Trusted Access prompts, and any hook in `hooks/*.py` are outside `settings.json`'s
  deny list entirely and outside this skill's reach by construction; if a request implies one of
  those, say so and stop (this should be rare -- it means the request misunderstands what this
  skill can touch, not that §21 grants any authority over them).
- Proceed if there is no explicit, action-specific operator consent for this exact change visible
  in the current conversation.

## Steps

1. **Identify the target file(s).** Default to `C:\Users\koros\.claude\settings.json` (the global
   file) unless the operator's request is scoped to a project (then also consider that project's
   own `.claude/settings.json` / `.claude/settings.local.json`). State which file you are about to
   edit.

2. **Read the file and locate the exact entries.** Read the current `permissions.deny` array. Find
   the precise entry/entries matching what the operator named. If the match is ambiguous (multiple
   entries could plausibly be "the .env rule"), list the candidates and ask which ones, rather than
   picking for the operator.

3. **Show the exact before/after.** In your reply, quote the exact current entry (or entries)
   about to change, and the exact resulting state (removed entirely, or narrowed to a more specific
   pattern if the operator asked for narrowing rather than removal -- prefer narrowing over full
   removal when the operator's stated reason supports it, e.g. scoping `Read(//**/.env.local)` down
   to `Read(//d/Repo/SomeProject/.env.local)` rather than removing the global pattern, if that is
   enough for what they actually asked to do). This is not a re-ask for consent (consent already
   happened) -- it is the audit-visible confirmation of exactly what is changing.

4. **Make the edit.** Use `Edit` on the settings file, changing only the named `permissions.deny`
   entries. Do not reformat or touch any other part of the file.

5. **Append an audit log entry.** Append one entry to
   `C:\Users\koros\.claude\logs\update-config-audit.log` (create the `logs` directory first if it
   does not exist -- do not use `New-Item -Force` on the file itself if it already exists, only
   create it if absent). Format, one line or a short block per entry:

   ```
   2026-09-03T19:40:00 | project=Ferma | file=C:\Users\koros\.claude\settings.json
   changed: removed "Read(//**/.env.local)" from permissions.deny
   reason: operator asked to create/populate D:\Repo\Ferma\.env.local with LLM provider API keys for AGENT-0-BENCH-1 testing
   ```

   Use the real current timestamp, the real project/repo this session is working in, the exact
   entries changed (verbatim, before -> after or "removed"), and the operator's actual stated
   reason from the conversation -- not a generic placeholder.

6. **Confirm in the reply.** State plainly what changed, that it takes effect for new tool calls in
   this session (a permission change made mid-session may need the specific tool call retried), and
   where the audit entry was recorded. Do not overstate scope -- if this was a global change,
   remind the operator it applies to every project/session on this machine, not just the one at
   hand.

## Worked example (the case that prompted this skill)

Operator: "используй эти ключи для тестинга" after explicitly authorizing, via a new CLAUDE.md
§21, that Claude may now act on this consent to remove the `Read(//**/.env.local)` entry so it can
create/write `D:\Repo\Ferma\.env.local`.

1. Target file: `C:\Users\koros\.claude\settings.json` (global, since the deny rule lives there,
   not in a project-local settings file).
2. Located entry: `"Read(//**/.env.local)"` in `permissions.deny`.
3. Before: `"Read(//**/.env.local)"` present. After: entry removed (the operator asked to be able
   to have Claude create/populate this specific file across a testing session, not narrowed to one
   path -- if a narrower ask had been made instead, e.g. "just for Ferma", narrow the pattern to
   `Read(//d/Repo/Ferma/.env.local)` instead of removing the global entry).
4. Edit `settings.json`, removing that one array entry.
5. Append the audit log entry as shown above.
6. Reply confirming the change, noting it is global (applies beyond this one repo), and that the
   original blocked tool call can now be retried.
