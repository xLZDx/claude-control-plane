# Rosetta

Rosetta is no longer an optional workflow you invoke when you remember to. It is the protocol,
recorded in PM Bridge and watched by hooks. The operator's instruction (2026-08-26): *"надо сделать
из розеты хук, чтобы все проходило через план/акт/валидейт и документировалось."*

The old version of this file ended with "Do not persist a session-wide reminder hook." That advice
was about a *reminder* -- text injected into every prompt, which is forgettable exactly when a
session is under load. What replaced it is not a reminder: the record lives outside the model, so
there is nothing to forget.

## The five phases

**1. Inspect.** Read the real state -- repository, tests, existing patterns, constraints. Free and
unrecorded: the protocol gates the Act phase, not this one. Read-only shell commands and the Read /
Grep / Glob tools are never touched by any of this.

**2. Plan.** `pm_rosetta_plan(project, repo, session_id, title, scope, steps, verification)`.
`session_id` is `$CLAUDE_CODE_SESSION_ID`. `verification` is stated **up front** -- how the work
will be proven, decided before it is convenient to decide. The plan starts `pending`: a plan is not
permission.

**3. GO.** GPT-PM approves the plan, not the operator (CLAUDE.md §16/§17 -- the operator holds only
the irreversible class in §4/§14). Send the plan, read the reply yourself, then
`pm_rosetta_go(plan_id, verdict, reply_excerpt)`. The approval binds to the plan's **hash**: any
material change means a NEW plan, and the old GO does not carry over. A verdict that is not an
APPROVE is refused outright, so a reply nobody read cannot become authorization.

**4. Act.** Work normally. Every mutating tool call is recorded automatically against the plan that
authorized it -- nothing to remember, nothing to write. Two records per call: intent, then outcome.

**5. Validate + Document.** `pm_rosetta_close(plan_id, result, evidence)`. **Evidence is mandatory
for `passed`** -- what was run, what it returned. `failed` and `blocked` need none, deliberately:
reporting bad news must never be the harder path.

The changed-set and the review class are reconstructed **from the repository** at closure -- git
status plus the commit range since the plan opened -- not from the act journal. A tool call records
what was attempted; only the repository knows what happened. A run that turns out to have touched
dependencies, CI, schema, secrets or the policy layer closes as HIGH whatever it declared.

## Transparency is not optional (operator instruction, 2026-08-26)

Rosetta used to be visible: the operator could read the plan in the session. Moving the record into
PM Bridge made it auditable and, at the same time, invisible — the plan became a JSON file in
gitignored runtime state that nobody sees. Operator, on watching a run: *"нее это так не пойдёт,
раньше роззетта работала прозрачно."* Four requirements follow, and none of them is satisfied by the
record merely existing on disk.

**1. Print the plan into the session, as prose.** Every plan, when it is opened and whenever it is
revised. Plain readable text — headings, numbered steps, the verification — **never a JSON dump**
(*"показывай план нормальным текстом а не джейсоном"*). The JSON is the machine's copy; the operator
gets the human one. Show the plan id, hash, status and whether it is approved, because those are what
make the record checkable rather than decorative.

**2. Ask GPT-PM for a Definition of Done, and do not write your own.** The GO request asks for two
things: approval, and the acceptance criterion. Per step and for the batch: what observable condition
means it is finished, what evidence the reviewer will require to believe it, and what would cause
rejection at the verification round. The implementer setting the acceptance criterion for their own
work is how a green suite comes to prove nothing — the failure this project has already recorded
several times. If a step's DoD cannot be met by the verification in the plan, that is a finding: say
which and what is missing, and narrow the claim rather than assert an untested one.

**3. The decision log records BOTH sides: what was planned, and what was actually done.** Not a
closing summary of the outcome — the plan as it stood, then the outcome against it, item by item.
A log that only records what happened cannot show what was abandoned, silently descoped, or quietly
replaced by something easier. Where they differ, the difference is the entry.

**4. The HTML report carries planned / DoD / status, per item.** Every report on a Rosetta-governed
run shows, for each planned item: what was planned, the Definition of Done GPT-PM set for it, and
whether it is **done, not done, or partial** — and for partial, **what the remaining tail is**.
A report that lists only completed work is a status claim, not a status report. Operator: *"сделано
или нет или частично с хвостами."*

These four are the visible surface of the protocol. The record on disk is evidence; this is what
makes the evidence readable by the person the work is for.

## Review class

Computed from the paths that actually changed. Never a judgement about your own work.

| class | what it means | closure notification |
| --- | --- | --- |
| `LOCAL` | docs, reports, comments, test fixtures -- nothing executable | skipped |
| `STANDARD` | ordinary source | GPT-PM notified |
| `HIGH` | dependencies, CI, migrations, secrets, `.claude/hooks`, settings | GPT-PM notified |

`LOCAL` skips **only** the closure notification. It never skips the plan and never skips the GO.
One approved plan may cover several small `LOCAL` acts, so a typo fix does not cost a four-minute
browser round-trip -- but it still happens under a plan.

## Where you are today: audit mode

R0 records and **denies nothing**. If you work without a plan, the calls go through and are marked
`governed: false`; the Stop hook tells you once, then lets the session end while recording that it
did. Enforcement switches on after Gate B, because an enforced GO needs to know which GPT-PM
conversation authorized the work, and today that binding still degrades to a folder-name
convention. Turning deny mode on first would authorize mutations off an identity mechanism the
roadmap is already scheduled to replace.

So: today Rosetta gives you a truthful record of what ran under what authority. Before it, nothing
anywhere knew that.

## When a hook tells you work is ungoverned

Do not argue with it and do not route around it. Write the retrospective plan, get the GO, close it
with evidence. The debt is real: those changes happened with nothing reviewing them.

## Where things live

- Protocol implementation: `D:\Repo\pm-bridge\src\rosetta.js`
- MCP tools: `pm_rosetta_plan`, `pm_rosetta_go`, `pm_rosetta_close`, `pm_rosetta_status`
- Hooks: `rosetta_audit.py` (PreToolUse + PostToolUse), `rosetta_due.py` (Stop), shared logic in
  `_rosetta_common.py`
- State: `D:\Repo\pm-bridge\state\rosetta\` -- `plans/`, `sessions/`, `spool/`
- Tests: `D:\Repo\pm-bridge\tests\test_rosetta_r0.mjs`,
  `C:\Users\koros\.claude\tools\test_rosetta_hooks.py`
- Kill switches: `CLAUDE_ROSETTA_GATE=off` (everything), `CLAUDE_ROSETTA_DUE_GATE=off` (the Stop
  check alone). Process-level, set before the session starts.

The spool is a compatibility layer, not a design: Gate C ingests it into the SQLite WAL ledger and
deletes it (`core/ROADMAP.md`).

## What this does not change

Nothing here touches CLAUDE.md §4 or §14. Force-push, history rewrite, `git reset --hard`,
`git clean -f`, branch deletion, branch creation's double consent, secrets, production, real money
-- still the operator's alone, and no plan, approval or review class substitutes for that.
